# Заметки о выполнении

## Время

На работу над прототипом потратил около **17 часов**. Это приблизительная оценка на 8 октября 2026 года, включая настройку окружения, реализацию, проверки и исправления. Точный поминутный учёт не вёл.

## Решения и компромиссы

- **React + TypeScript и FastAPI.** Разделил клиент и сервер, чтобы явно выделить контракт API и серверную проверку доступа. Серверный код организовал по модулям `auth`, `documents` и `rag`, клиентский — по функциональным модулям.

- **Серверная сессия.** Для авторизации использовал cookie со случайным токеном. Пользователя и его роль сервер определяет по собственным данным. Переданная клиентом роль в JSON, query-параметрах или заголовках не расширяет доступ.

- **Проверка прав до поиска и модели.** Вынес правило доступа в `DocumentStore` и использовал его как при выборе источников, так и при прямом чтении документа. Отдельными серверными тестами проверил состав контекста, передаваемого mock-модели.

- **Независимые роли.** Выбрал следующую политику: `user` видит общедоступные документы, `hr` — общедоступные и HR-документы, `admin` — общедоступные и административные. Автоматический доступ администратора к HR-документам не предусмотрел, поскольку задание явно его не требует. При изменении требований правило можно скорректировать в `DocumentStore` и матрице тестов.

- **Одинаковый ответ 404.** Для отсутствующего и запрещённого документа возвращаю одинаковые код и сообщение, чтобы через этот ответ не раскрывалось существование закрытого документа.

- **JSON и память процесса.** Для шести документов использовал JSON-файл, без БД, миграций и отдельного индекса. Корпус проверяется при старте. Сессии хранятся в памяти процесса и сбрасываются при перезапуске сервера.

- **Поиск по словам.** Реализовал простой алгоритм совпадения ключевых слов, достаточный для условий задания. Результаты сортируются по оценке совпадения, затем по ID, чтобы порядок оставался детерминированным.

- **Детерминированный mock.** Вместо настоящей модели использовал соединение текстов выбранных источников. Ссылки сервер формирует из того же набора документов. Если разрешённых совпадений нет, ответ «Недостаточно данных» возвращается без вызова модели.

- **Axios и проверка ответов.** Вынес HTTP-запросы, обработку ошибок и отмену запросов в общий слой. Для проверки структуры ответа использовал Yup. При `401` интерфейс сбрасывает локальное состояние авторизации. Текст ответа отображается средствами React.

- **Vite proxy.** Настроил проксирование `/api`, чтобы при локальном запуске браузер работал с одним origin. Production-раздачу сборки и отдельный reverse proxy в объём прототипа не включал.

- **Тесты двух уровней.** Через pytest проверил серверные ограничения, сессии и контекст модели. Через Playwright — пользовательские сценарии, cookie и переходы между страницами. Для блока результата использовал `data-testid`, чтобы не связывать тест с именами SCSS-классов.

- **Проверка ошибки сервиса.** Отдельный режим сбоя через переменную окружения решил не добавлять. Исключение модели воспроизводится серверным тестом, а отображение HTTP 503 — перехватом ответа в Playwright. Для ошибочного сценария на защите выбрал прямое открытие закрытого документа под обычным сотрудником.

## Проверки и исправления

Проверил установку зависимостей и запуск проекта в новой копии репозитория на Windows:

- 49 серверных тестов прошли;
- 8 браузерных тестов прошли;
- ESLint завершился без ошибок;
- проверка TypeScript и production-сборка завершились успешно.

При настройке E2E согласовал локатор блока ответа `data-testid="ask-result"` с разметкой интерфейса и исправил обработку сообщения об ошибке сервиса.

При сохранении логов через PowerShell столкнулся с искажением кириллицы и отображением обычных сообщений Uvicorn из stderr как `NativeCommandError`. Для сохранения читаемого вывода использовал перенаправление через `cmd` и последующее чтение файла в UTF-8.

Проверки запускал локально. Состав логов, скриншотов и команды их получения описал в [материалах проверки](evidence/README.md).

## Границы mock

- Использовал статические демонстрационные учётные записи. Интеграции с корпоративным провайдером идентификации нет.
- Подготовил шесть синтетических документов. Они не являются реальными регламентами компании «Автотор».
- Поиск работает по словам, без embeddings, векторной БД, синонимов и морфологического анализа.
- `DeterministicMockModel` не обучается, не обращается к внешней модели и не составляет смысловое резюме.
- Подмена HTTP 503 используется только в одном E2E-сценарии. Остальные браузерные сценарии обращаются к работающему FastAPI.

## Ограничения и оставшиеся проблемы

1. **Хранение сессий.** Сессии не переживают перезапуск и не разделяются между процессами. Прототип рассчитан на один worker Uvicorn.

2. **Демонстрационная аутентификация.** Тестовые пароли открыто заданы в коде. Регистрацию, восстановление пароля, ограничение частоты запросов и полноценный аудит входов не реализовывал.

3. **Локальный HTTP.** Для cookie установлено `Secure=False`. При внешнем размещении потребуются HTTPS, production-настройки cookie и защита изменяющих запросов от CSRF с учётом выбранной схемы размещения.

4. **Статический корпус.** Управление документами и динамическое изменение прав не реализованы. Документы читаются при запуске, а проверка их количества привязана к условию задания: три общедоступных, два HR и один административный.

5. **Качество поиска.** Поиск чувствителен к словоформам, не учитывает смысл и возвращает все разрешённые совпадения. Ограничение размера контекста не реализовано.

6. **Синхронный интерфейс модели.** Для подключения настоящей модели потребуется адаптировать выполнение длительных операций, добавить таймауты и обработку отмены. Блокирующий сетевой вызов нельзя оставлять непосредственно внутри асинхронного маршрута.

7. **Риски реальной генерации.** Достоверность ответов, prompt injection, корректность цитат и допустимость передачи корпоративных данных требуют отдельной проработки. Проверка прав доступа сама по себе эти вопросы не решает.

8. **Границы тестирования.** Проверил основные сценарии задания. Нагрузочные испытания, полноценный аудит безопасности и проверку доступности интерфейса не проводил. E2E запускал в Chromium на Windows; другие браузеры и ОС отдельно не проверял.

9. **Эксплуатация.** Production-деплой, CI, мониторинг и централизованный сбор логов не настраивал.

## Что изменил бы для реальной интеграции

Для реального использования я бы подключил корпоративную идентификацию и проверяемые сервером права, вынес сессии в общее хранилище, а документы и метаданные — в постоянное хранилище.

Добавил бы загрузку, версионирование и разбиение документов на фрагменты с наследованием прав доступа. При замене поиска сохранил бы фильтрацию по ACL до передачи контекста модели, включая поиск по индексу, повторное ранжирование и работу с кэшем.

Вместо mock реализовал бы адаптер модели с ограничением размера контекста, таймаутами, отменой запросов и обработкой недоступности. Проверял бы, что возвращаемые цитаты относятся к разрешённым источникам.

Расширил бы тесты сценариями утечек между пользователями и организациями, проверками качества ответов и вредоносных инструкций внутри документов. Дополнительно уточнил бы требования к хранению и передаче данных, настроил безопасное журналирование и инфраструктуру эксплуатации.

Сопоставление текущих компонентов и необходимых изменений привёл в [схеме интеграции](docs/INTEGRATION.md).

## Использование ИИ

В работе использовал **ChatGPT**: для обсуждения архитектуры и API, подготовки вариантов клиентского и серверного кода, тестов, разбора ошибок, описаний PR, документации и схем интеграции.

Предложенные изменения применял и адаптировал к проекту, запускал приложение и проверки локально, разбирал полученные ошибки и принимал решения об объёме реализации. Например, решил отказаться от отдельного режима сбоя сервиса как избыточного для этого задания.

Документацию подготовил с помощью ИИ на основе кода проекта и результатов своих проверок. Указанные результаты тестов получил при локальном запуске.

Во время работы самого приложения внешний ИИ-сервис не используется: запросы обрабатывает локальный детерминированный mock.
